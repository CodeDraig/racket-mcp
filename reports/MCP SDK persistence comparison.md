# Compare How MCP SDKs Store State

Most MCP SDKs do not require an application to run a separate database server. The protocol also does not prescribe a database product. The bigger difference is what each SDK persists: many provide optional stores for task records, results, OAuth tokens, sessions, or HTTP event replay, while this Racket repo includes a durable workflow runtime that checkpoints stages and effect intents in SQLite. A durable task record does not automatically restart the computation that produced it. FastMCP, a separate Python framework, comes closest to bundling an execution queue, and offers an in-memory mode as well as Redis-backed durability. This comparison is a read-only snapshot dated October 24, 2026; moving repository branches and protocol revisions are identified where they matter.

## MCP requires retrievable task state, not a database brand

The pinned 2026-07-28 Tasks specification requires the server to make a created task retrievable before returning its handle. It defines protocol-visible state such as status and final result, and names no storage engine. The spec describes external job APIs as a natural fit; it does not direct SDKs to embed SQL, or prescribe how application code should resume after a crash. Those are separate runtime choices. ([2026-07-28 Tasks specification](https://tasks.extensions.modelcontextprotocol.io/specification/2026-07-28/tasks))

The official SDKs reflect that distinction, though their feature coverage is changing. Ordinary server and client setup does not require a database in the reviewed TypeScript, Python, C#, Go, Rust, Java, or Kotlin docs. Some SDKs supply replaceable persistence interfaces when they implement a feature that needs storage; some implement only in-memory state; and some do not yet expose a first-class server task store at the inspected version. None of this prevents an application from implementing its own JSON-RPC handlers or connecting to a job system.

## FastMCP adds a configurable worker queue

FastMCP is a separate Python framework, rather than the current official Python SDK's persistence model. Its v2 background-task docs describe Docket with `memory://` as the ephemeral, single-process default; Redis or Valkey provides persistence across restarts and workers across processes or machines. FastMCP 4 reached GA on August 31, 2026, supports protocol revision 2026-07-28, and moved Tasks to an optional `fastmcp-tasks` package that continues to use Docket. ([FastMCP v2 task docs](https://gofastmcp.com/v2/servers/tasks), [FastMCP 4 announcement](https://blog.gofastmcp.com/3mufbh2vcv22o))

That makes FastMCP the closest reviewed comparison for queued background work: the app can start without a remote store, then opt into an external service for durable, distributed workers. Its task documentation establishes queue/worker persistence. The sources reviewed do not establish Racket-style named stage checkpoints or manual recovery around individual external effects. Those execution semantics should not be inferred from Redis retaining a task or Docket recovering a worker. FastMCP also configures OAuth client storage and SSE event replay separately, illustrating that a framework can have several distinct persistence backends. ([OAuth proxy storage](https://gofastmcp.com/v2/servers/auth/oauth-proxy), [HTTP event storage](https://gofastmcp.com/v2/deployment/http))

## Racket SQLite backs a wider execution model

Here, SQLite is embedded in the Racket process: the package uses Racket's `db` library and calls `sqlite3-connect`; it does not require a running database service. Both the file store and `open-memory-store` use SQLite. The file-backed store enables WAL and foreign keys, stores instance state and arguments as JSON with provenance columns, keeps a journal and continuation-token mapping, and wraps work in immediate transactions. It also creates a sibling `.workers` directory for inter-process worker locks. ([storage implementation](/srv/data/code/racket-mcp/mcp/storage.rkt:23), [schema](/srv/data/code/racket-mcp/mcp/private/storage-schema.rkt:11), [transaction supervisor](/srv/data/code/racket-mcp/mcp/private/transaction.rkt:41), [worker locks](/srv/data/code/racket-mcp/mcp/private/worker-lock.rkt:24))

The local state is more than task status and result. Workflow rows preserve stage position, values, effect records, ownership, expiry, and executable identity. For a manual effect, the runtime commits an intent before calling the effect adapter; if the outcome is uncertain after interruption, explicit recovery resolves it. Restart tests exercise SQLite reopening and observed-outcome recovery in child processes. ([workflow state](/srv/data/code/racket-mcp/mcp/workflow.rkt:68), [identity checks](/srv/data/code/racket-mcp/mcp/workflow.rkt:74), [effect intent path](/srv/data/code/racket-mcp/mcp/workflow.rkt:285), [restart test](/srv/data/code/racket-mcp/tests/restart.rkt:13))

The SQLite store also hosts opt-in OAuth registration state and the durable change outbox/cursors, while the resource cache remains in memory. Serving requires an explicit state file when the interface contains durable workflows or upstream bridges; a simple stateless interface can run without one. So the engine is coupled to SQLite when these durable features are used, but the repo does not force a database service on every MCP server. ([OAuth registration table](/srv/data/code/racket-mcp/mcp/oauth-registration-store.rkt:43), [external-change transaction](/srv/data/code/racket-mcp/mcp/external-changes.rkt:78), [in-memory resource cache](/srv/data/code/racket-mcp/mcp/private/resource-cache.rkt:8), [serving state requirement](/srv/data/code/racket-mcp/mcp/private/interface-serving.rkt:8))

## The design tradeoff is integration versus backend choice

This repo makes a stronger runtime choice than the official SDKs surveyed: one built-in SQLite store supports checkpoints, idempotency keys, journals, task state, outbox entries, and recovery. For local use that buys a single file, no separate service, and a ready-made execution model. It also means applications using those durable paths inherit the SDK's SQLite schema, locking behavior, lifecycle, and filesystem requirements. Other SDKs generally expose a narrower store interface for one feature or leave the durable execution system to the application; FastMCP packages a worker queue and offers memory or external Redis/Valkey modes.

The practical comparison is therefore not “database versus no database.” It is **what state must survive, and who owns the restart logic?** Persisting a protocol task record makes its handle queryable; persisting a queue can recover a job dispatch; checkpointing application stages can resume a known step and require a decision when an external effect may already have occurred. These guarantees are distinct. This review establishes that Racket chose the deepest integration among the surveyed implementations; it does not establish that SQLite is atypical or unsuitable for the repo's local, single-host execution model.

**Method and limits:** This was a read-only source and documentation comparison. No SDKs were installed and no new runtime or restart tests were run; I inspected the repo's existing restart test source. Several upstream docs are on moving `main` branches; the report identifies tagged or immutable snapshots where the notes found them. The report and supporting notes are new files; repository code was not changed.
