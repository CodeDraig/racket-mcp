# MCP SDKs replaced Tasks as protocols changed

The Python and TypeScript SDKs removed their earlier experimental Tasks runtimes because the protocol design they implemented was being replaced, and keeping that code would mean supporting a moving, incompatible target. **Python’s removal PR said the old implementation represented roughly 13,000 lines to maintain and explicitly left re-adding the feature in its new form open.** The protocol proposal also names concrete problems with the old Tasks design: brittle capability negotiation, a blocking result flow tied to long-lived SSE connections, and task-list authorization that no longer fit sessionless MCP. The work moved to an optional extension so it could mature through implementation feedback outside the core release cycle. This is evidence of retiring the old wire contract and its SDK runtime, not a general rejection of asynchronous Tasks or persistence. The public sources reviewed do not cite SQLite or database burden as a reason.

## The old Tasks contract no longer fit MCP’s direction

The original Tasks feature was an experimental design from the 2025 protocol generation. The replacement proposal describes it as a stopgap while MCP’s extension mechanism was being formalized. Moving Tasks onto the Extensions Track let its wire contract evolve with implementation feedback outside core release timing; the proposal says promotion to core could follow once the extension was stable and broadly adopted. ([SEP-2663](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2663-tasks-extension.md); [merged proposal PR](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2663))

The proposal gives several specific reasons for redesign. **Negotiating the old feature required clients to coordinate multiple signals**: a method-level task capability, task support advertised per tool, and a task flag on each call. In practice, a client first had to list tools to know whether it could make a task-enabled call. The new extension instead uses one extension capability, then lets the server decide whether a given eligible request should return a task. ([SEP-2663, motivation](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2663-tasks-extension.md))

The old `tasks/result` interaction could also make a client hold an SSE connection open for the whole job, because the server needed that route to issue mid-task sampling or elicitation requests. This was burdensome and conflicted with a parallel protocol change disallowing unsolicited server-to-client requests. The old `tasks/list` method had a different problem: servers needed to prevent one caller from seeing or cancelling another caller’s tasks, but MCP had no universal caller-ownership rule. Sessions might have provided a scope, but session-removal work eliminated that option. Client-hosted Tasks had the same protocol conflict when they depended on unsolicited server requests. ([SEP-2663](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2663-tasks-extension.md); [SEP-2260](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2260-require-server-requests-to-be-associated-with-client-request.md); [SEP-2567](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2567-sessionless-mcp-via-explicit-state-handles.md))

The redesigned extension changes those interactions: servers return a task handle, clients poll state with `tasks/get`, and client input goes through `tasks/update`; it removes global task listing. That is a protocol and API break, so SDKs carrying the earlier runtime could not simply keep it unchanged and claim support for the new extension. ([2026-07-28 Tasks specification](https://tasks.extensions.modelcontextprotocol.io/specification/2026-07-28/tasks))

## Python and TypeScript removed the superseded implementations

Python’s removal record is unusually direct. PR #2714, merged June 2, 2026, says: “Keeping the experimental implementation around would mean maintaining ~13k lines against a moving target that no longer matches the spec.” The PR left the door open to re-add Tasks in the new form. This supports a concrete maintenance-cost explanation, but the cost was maintaining code for the superseded design during protocol churn; the PR does not say durable execution or persistence was a mistake. ([Python removal PR #2714](https://github.com/modelcontextprotocol/python-sdk/pull/2714))

TypeScript’s PR #2128, also merged June 2, removed its old experimental `TaskManager` and task-interception APIs because “tasks moved to Extensions Track.” The PR also described removal as unblocking dispatch-core extraction. Its stated rationale does not mention database burden or user rejection of Tasks; SEP-2663 supplies the broader protocol rationale. ([TypeScript removal PR #2128](https://github.com/modelcontextprotocol/typescript-sdk/pull/2128); [SEP-2663](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2663-tasks-extension.md))

The same month’s changes should not be read as two SDK teams independently deciding that asynchronous work should disappear. The protocol itself had withdrawn and redesigned the earlier feature. Python’s later reluctance to include replacement code in its core package was a separate packaging decision: maintainers discussed a standalone extension unless user demand justified in-repo support. ([Python tracking issue #2806](https://github.com/modelcontextprotocol/python-sdk/issues/2806))

## Tasks continued, with uneven replacement support

“Abandoned” is too broad. The 2026 specification continues Tasks as an optional extension and describes them as durable task state that can be retrieved later. It requires the server to make a task retrievable before returning its handle, but it names no database and does not require the SDK to checkpoint arbitrary application code or resume a handler at a saved workflow stage. It also points to external job APIs as a natural fit. ([Tasks specification](https://tasks.extensions.modelcontextprotocol.io/specification/2026-07-28/tasks))

Implementation has lagged the redesign in some SDKs. As checked around October 24–25, 2026, Python’s roadmap still listed the new extension as unimplemented. Its open PR #3005 proposed only part of the server lifecycle and deferred input updates and other pieces, so it does not count as shipped support. TypeScript’s separate `ext-tasks` package provides requester helpers, schemas, and a receiver for the legacy 2025 interaction; its published documentation does not claim a complete 2026 server-side task engine. ([Python roadmap](https://github.com/modelcontextprotocol/python-sdk/blob/main/ROADMAP.md); [Python PR #3005](https://github.com/modelcontextprotocol/python-sdk/pull/3005); [TypeScript `ext-tasks` README](https://github.com/modelcontextprotocol/ext-tasks/blob/main/packages/ext-tasks/README.md))

The official C# SDK provides a useful counterexample to blanket abandonment: its v2 Tasks extension replaces the earlier experimental implementation. This illustrates the broader pattern: remove an incompatible implementation, then decide separately whether and where to implement the replacement. ([C# SDK versioning](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/docs/versioning.md))

## The evidence does not blame SQLite

The sources support protocol incompatibility and maintenance of the obsolete Python implementation as reasons for removal. They do **not** support the claim that these SDKs dropped Tasks because they objected to durable persistence, SQLite, or checkpointed workflows. The new extension still requires durable protocol-visible task state to be retrievable; it leaves the backing job system and application execution model to implementations.

That distinction matters for this Racket repository. Its SQLite runtime persists workflow stages, values, effect intents, and recovery information ([workflow implementation](/srv/data/code/racket-mcp/mcp/workflow.rkt:68)). Those guarantees go beyond a protocol task handle and result. The SDK removals show the cost of coupling an implementation to an unstable wire design; they do not show that a local durable workflow engine is inherently outside the useful scope of an SDK. No code changed and no tests ran for this read-only source and history review. The remaining uncertainty is whether Python will complete PR #3005 or ship another implementation of the redesigned extension.
